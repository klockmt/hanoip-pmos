# hanoip-pmos

postmarketOS port for the **Moto G60 (hanoip, XT2135-1)**: a working downstream-kernel (4.14) build, to become our own hardened server kernel; the mainline-kernel effort is parked (`docs/STATUS.md`, section 5).

The rules (commits, personal data, flashing, SSH and security, tests for bugs) are in `AGENTS.md`. This file is the log of the device and its investigations; what works is in `docs/STATUS.md`.

## Device

- SoC SM7150 (`qcom,sdmmagpie`, soc_id 365). `ro.board.platform=sm6150` is Motorola's platform name, not the SoC.
- 4 GB RAM, 128 GB UFS, A/B, unlocked bootloader, boot image header v3, LineageOS 22.1 before pmOS replaced it.
- Verified facts: `docs/device-info/SUMMARY.md`. Read it before touching device info.
- Partition backups (boot, vendor_boot, dtbo, vbmeta, persist, modemst, fsg, misc, abl + SHA256SUMS): `$HANOIP_BACKUP_DIR/`. They stay out of the repo on purpose.
- Collection of 2026-10-23 (`scripts/collect-device`, already fixed for A/B): `$HANOIP_COLLECTION_DIR/` with identity, kernel (config, dmesg, iomem), slot `b` partitions, `/vendor` firmware (102 MB, proprietary) and the device tree. It contains serial/MAC/IMEI and firmware: **never copy it into the repo**. `.gitignore` covers `*.img` and the collection folders.
- `docs/device-info/android-runtime.txt`, `running.dts` and `running.dtb` are **sanitized** (MACs became `00:00:00:00:00:00`, the serial became `X`); sanitize again before committing if you regenerate them.

They read `.env`; the ones that change something accept `DRY_RUN=1`. `README.md` says exactly which were run end to end and which only in dry-run, so keep it honest when you change them.

## pmOS downstream working (2026-10-24)

- **postmarketOS edge boots on its own with SSH** on the downstream kernel (cool585 Cybertron v18, 4.14) with openrc. Root is expanded to 104 GB on `userdata`. Access: `scripts/hanoip-ssh` (uses `HANOIP_USER`, `HANOIP_HOST` and `HANOIP_SSH_KEY` from `.env`; dedicated key without a passphrase, since the user's own key has one and cannot be used non-interactively). `sudo` asks for a password.
- Packages in the local pmaports: `device/downstream/linux-motorola-hanoip` (cool585 source at commit `b92cb6cd`, config from `/proc/config.gz` + `DEVTMPFS`, `DEVTMPFS_MOUNT`, `USB_CONFIGFS_ECM/RNDIS`, `SYSVIPC`, `FHANDLE`; installs `Image.gz` and the base DTB `qcom/sdmmagpie-hanoi-base.dtb`) and `device/testing/device-motorola-hanoip` (`kernel-downstream` subpackage). `pmbootstrap config kernel downstream`, `service_manager openrc`, `ssh_keys True`.
- `deviceinfo`: `header_version 3`, `initfs_compression lz4`, `dtb qcom/sdmmagpie-hanoi-base` (goes in `vendor_boot`; the stock `dtbo` applies the board overlay), `bootimg_custom_args` with base `0`, offsets `0x8000`/`0x1000000`/`0x100`, `dtb_offset 0x1f00000`, `os_version 15.0.0`, `os_patch_level 2025-04`; cmdline with the non-Android options of the stock `vendor_boot`; `rootfs_image_sector_size 4096`.
- With v3, pmOS puts the **initramfs, cmdline and DTB in `vendor_boot`** and only the kernel in `boot.img`. Flash both.
- **Mandatory patch for the 4.14 kernel:** `0001-loop-rescan-partitions-after-block-size-change.patch` (re-read the partition table on `LOOP_SET_BLOCK_SIZE`). Without it, `losetup -P --sector-size 4096` does not create `loopNpX`. With a 512-byte GPT the initramfs `fdisk` cannot find the table (UFS has 4096-byte sectors). Together these two problems prevented mounting the subvolumes.
- Kernel build: tree `$KERNEL_DOWNSTREAM_DIR`, `make O=.output ... DTC=/usr/bin/dtc` (the tree's own `dtc` built with clang 23 segfaults), then `pmbootstrap build --envkernel linux-motorola-hanoip` (without activating envkernel).
- **Motorola's fastboot refuses to flash `userdata`** (`flash permission denied`). Flash the rootfs through the Lineage recovery: restore the stock `vendor_boot_b`, `fastboot reboot recovery`, Enable ADB, `adb exec-in "dd of=/dev/block/by-name/userdata bs=4M" < motorola-hanoip.img`, and verify the hash by reading it back. Writing over the initramfs USB network (`nc`) froze the network midway; do not use it.
- **Firewall solved (24/10):** nftables built into the kernel (`NF_TABLES`, `NF_TABLES_INET/IPV4/IPV6`, `NFT_CT`, `NFT_COUNTER`, `NFT_NAT`, `NFT_MASQ`, `NFT_REJECT*`, `NFT_LIMIT`, `NFT_LOG`, `NFT_CHAIN_NAT_IPV4`) and **the set backends** `NFT_SET_HASH`, `NFT_SET_RBTREE`, `NFT_SET_BITMAP` (without them rules with `{ ... }` fail with "Not supported"). No modules: the kernel package does not install modules, so everything is `=y`. Config in `linux-motorola-hanoip/config-motorola-hanoip.aarch64` (`pkgrel=2`). The `51_usb_inet.nft` rule allows everything coming in over USB.
- Updating only the kernel: `scripts/mkbootimg-kernel` (the pmOS v3 `boot.img` is just the kernel), test with `fastboot boot`, then `fastboot flash boot_b`.
- Pending: none from the 2026-10-30 list; zram works since 2026-11-01 (see "Zram swap" below) and `systemd-tmpfiles`/`sysusers` are harmless on 4.14.
- **Large transfers over the USB (NCM) network bring the device network down** (ARP `INCOMPLETE`, only a reboot recovers it). Limit with `pv -L 1m` (69 MB went through that way); `scripts/push-firmware` does this.
- Rebooting to the bootloader without buttons: `scripts/reboot-bootloader` (the `reboot(RESTART2, "bootloader")` syscall).
- Without `FW_LOADER_USER_HELPER_FALLBACK`, boot-to-SSH drops from ~3 min to seconds (every missing firmware file cost 60 s).

## Modem and Wi-Fi (works since 2026-10-30)

Details, files and build in `userspace/modem/README.md`. **Solved on 2026-10-30:** the modem firmware reads SMEM item 134 (`mmi_unit_info`), written by Motorola's `mmi_info` driver, which our config had off (`CONFIG_MMI_INFO`, which also needs `CONFIG_MMI_ANNOTATE`; the stock `hanoip_defconfig` has both). With them `icnss` reaches `FW_READY` and `wlan0` associates through NetworkManager, WPA3 included. `hanoip-modem` is now in the `default` runlevel. Summary of the investigation before that:
- Kernel with `QCA_CLD_WLAN=y` and `FW_LOADER_USER_HELPER_FALLBACK` off: the package `linux-motorola-hanoip` then was `pkgrel=3` (it is at 12 now) with exactly the config and patches `0001`-`0003` of test kernel #10 and correct `sha512sums` (the old checksum was stale), but it was never built by pmbootstrap itself, only through `scripts/build-kernel` + `--envkernel`; tested only with `fastboot boot` (`$HANOIP_TEST_DIR/pmos-wlan/boot-wlan.img`). `boot_b` still holds build #4, without WLAN.
- On the device (before 2026-11-01 by hand, now from the `device-motorola-hanoip-modem` subpackage): Alpine's `rmtfs` (read-only, `-r`); `qrtr-ns` v1.0, `pd-mapper` and `tqftpserv` with patches; the udev and openrc files. Still from the phone itself: firmware in `/lib/firmware` and `/var/lib/tqftpserv` copied from `persist` (ro,noload).
- Requirements found: a userspace QRTR name server; remoteproc fallback to `/lib/firmware`; `fsg` → `fsg_b` link (without it, `rmts_get_buffer api failed`); IPA up (`echo 1 > /dev/ipa`) and ready (`rmnet_ipa0`) **before** the modem; `restart_level` set to `RELATED`.
- Result: modem `ONLINE`, `wlan_pd` comes up and WLFW connects, but the Wi-Fi firmware crashes 0.7 s later (`early crash indication`, `EX:kernel:0x0:tmr_slave1:0x1d1`), in a loop, before `FW_READY` and without ever asking for `bdwlan`. DT, IPA order and `/readwrite` are already ruled out. (That crash was the missing SMEM item; see above.) Every test needs a clean boot (the modem does not restart well within the same session).
- Test kernel #6 (`$HANOIP_TEST_DIR/pmos-wlan/boot-wlan-debugfs.img`) enables `DEBUG_FS` (needs patch `kernel/downstream-patches/0002-...`; previous config in `.output/.config.pre-debugfs`). It showed that the `icnss` QMI handshake finishes without errors (`board_id 0xff`, fw `WLAN.HL.3.2.2-00947`) and the firmware crashes by itself about 650 ms later. Details in the modem README.
- 2026-10-24 (afternoon): `icnss` now sends `host_cap`, REGDB and BDF like `cnss-daemon` (patch `0003`, test kernel #10 `$HANOIP_TEST_DIR/pmos-wlan/boot-wlan-regdb.img`). The firmware accepts everything and **still crashes**. Details and discarded hypotheses in the modem README. Patches `0002` and `0003` are in `kernel/downstream-patches/` and in the pmaports kernel package (the copies in `pmaports/device/downstream/linux-motorola-hanoip/` must stay identical to the ones in `kernel/downstream-patches/`; if you change one, change both and recompute `sha512sums`).
- Never use `pkill -f <text>` inside `ssh ... 'sudo sh -c "..."'`: it matches the command line itself and kills the session (it happened twice). Keep the PID with `$!`.

## Screen console and boot log (2026-10-24)

The screen used to stay on the Motorola logo for the whole boot. What was found and done:
- The **ABL rewrites every `console=` on the command line to `console=null`** (checked with `console=ttyMSM0` in vendor_boot and `console=tty0` in the boot.img header: both arrive as `console=null`). `ignore_loglevel` and `fbcon=` pass through. The DTB only contributes `quiet rcupdate.rcu_expedited=1 rcu_nocbs=0-7 noirqdebug kpti=off mitigations=off`. So the kernel got no console at all. Patch `0004` makes `console=null` mean `tty0`.
- **The MSM fbdev emulation cannot work** with this downstream SDE driver: `msm_fbdev.c` asks for an iova with `priv->kms->aspace`, which SDE never fills (it keeps `sde_kms->aspace[domain]`), hence `failed to get buffer obj iova: -22`. Not worth fixing: the first fbdev modeset would also have to pass the SDE pipeline.
- Patch `0005` adds `hanoip-splashfb`: a plain fbdev on the `cont_splash_region` (`0x9c000000`, 1080x2460, 32 bpp, stride 4320, **a8r8g8b8 / BGRA bytes**, found by reading the buffer) that the bootloader leaves scanning out. It maps the pages write-combined with `vmap` because that region is RAM without `no-map`, which arm64 refuses to `ioremap` (so `simplefb` cannot be used). It does not touch the display pipeline, and only registers if the reserved-memory node exists. fbcon takes it over at 0.35 s: 90x111 characters with the 12x22 Sun font (the largest in this tree; no Terminus 16x32 in 4.14 here). The raw buffer is in debugfs (`/sys/kernel/debug/hanoip_splashfb`): render it with PIL (`Image.frombuffer('RGBA',(1080,2460),data,'raw','BGRA',4320,1)`) to see exactly what is on the screen without a camera.
- Config: `FRAMEBUFFER_CONSOLE`, `FONTS`, `FONT_SUN12x22`, `FONT_10x18`, `FB_HANOIP_SPLASH`; `DRM_FBDEV_EMULATION` off (it only logs the iova error). `scripts/config -e FONT_SUN12x22` does not work (lowercase x): edit `.config` and run `olddefconfig`.
- Command line (in `scripts/mkbootimg-kernel` and `deviceinfo`): `ignore_loglevel fbcon=font:SUN12x22`. `ignore_loglevel` shows the whole boot log but also every `[signal] ... send death sig` line the Motorola kernel prints for each signal, which scribbles over the login prompt, so `hanoip-console.start` (installed in `/etc/local.d` by the device package, or by `scripts/setup-console`) switches it off and sets `dmesg -n 4` at the end of boot. Checked by rendering the buffer before and after.
- State after the framebuffer works: OpenRC boot output (coloured `[ ok ]`), then `Welcome to Nura! ... motorola-hanoip login:` on tty1. Still noisy in that log: `systemd-sysusers`/`tmpfiles` fail on 4.14 ("Failed to chase and open directory").
- **A/B retry counter (found 2026-10-24, important for a server):** each boot of a slot that was never marked successful costs one retry; after ~7 the ABL sets `unbootable=yes` on it and switches the active slot (here to `a`, which holds the old Lineage `boot_a`/`vendor_boot_a`, so nothing useful boots and the phone drops to the bootloader). Android marks the slot successful; pmOS does not. Seen as `fastboot getvar slot-retry-count:b` = 0, `slot-unbootable:b` = yes, `slot-successful:b` = no, `current-slot` = a, after a day of reboots. The fix is the `qbootctl` OpenRC service, which runs `qbootctl -m` at every boot: the device package now depends on `soc-qcom-qbootctl` (as `device-qcom-sm7150` does). A phone installed before that needs it installed by hand: `apk add soc-qcom-qbootctl` (packages `qbootctl`, `qbootctl-openrc` from Alpine edge community; `soc-qcom-qbootctl`, `-openrc` from the pmOS repo, which can be installed offline with `apk add --no-network`), then `qbootctl -m`. On the phone flashed before the dependency existed, `soc-qcom-qbootctl` (signed by the pmOS repo) is rejected as UNTRUSTED because its key is not installed, so install only the two Alpine packages (`qbootctl`, `qbootctl-openrc`) and run `rc-update add qbootctl default`; that is what was done on 2026-10-24. Verified end to end: after `fastboot set_active b` (flags `successful=no`, `retry=7`) a plain reboot left slot b `successful=yes` with no manual step. OpenRC lists the service as `crashed` (it runs one command and exits instead of daemonizing); that is cosmetic, and the boot log shows `SLOT _b: Marked boot successful`. Since commit `38c9a70` the device package runs `qbootctl -m` from `/etc/local.d/` instead (its post-install takes the `qbootctl` service out of `default`), so the `local` service must stay in `default`.
- Recovery when it happens: `fastboot set_active b` (restores retries and clears `unbootable`; the user allowed it, see the working rules), then `fastboot reboot`. With slot `a` active `fastboot boot` of pmOS images does not work either, because vendor_boot comes from the active slot.
- **Open: not yet seen by eye** (only through the scanout buffer).

## Boot test results (`fastboot boot`, nothing flashed)

- **First boot with signs of life (2026-10-24), downstream path:** header **v3** + stock `vendor_boot` and `dtbo` (slot `b`) + Cybertron kernel (stock or rebuilt) + own ramdisk. The device brought up the **NCM** USB gadget and answered ping at `172.16.42.1`.
- **pmOS initramfs runs (2026-10-24):** rebuilt downstream kernel + pmOS initramfs recompressed as LZ4 legacy + `pmos.debug-shell`, in v3 with stock `vendor_boot`/`dtbo`: ping in 20 s and a shell on `telnet 172.16.42.1 23`. UFS ok (104 partitions), `a600000.dwc3` ok, 3.6 GB RAM free, no `wlan0` yet. Image: `$HANOIP_TEST_DIR/downstream/boot-downstream-pmos-lz4.img`. The ABL cmdline includes the serial and MACs: do not copy its output into the repo.
- **The ramdisk must be LZ4 legacy** (`lz4 -l`, magic `02214c18`), like the stock ones. With gzip or zstd the device stalls on the Motorola logo, with no USB and no reboot. pmOS mkinitfs produces zstd by default: use `deviceinfo_initfs_compression="lz4"` (check that it produces legacy).
- Own test initramfs: `$HANOIP_TEST_DIR/downstream/root/` (**static** busybox, Alpine's `busybox.static`; the dynamic musl busybox makes init die). `init-reboot` (static C) reboots into recovery with `reboot(RESTART2, "recovery")` and proves that init ran.
- On the PC: NetworkManager connection `hanoip-usb` with `172.16.42.2/24` on the USB interface (created with `nmcli`, no sudo). The interface showed up as `enp5s0f3u1` (depends on the USB port).
- Rebuilt downstream kernel: `$KERNEL_DOWNSTREAM_DIR/out/` with the `/proc/config.gz` config + `DEVTMPFS`, `DEVTMPFS_MOUNT`, `USB_CONFIGFS_ECM`, `USB_CONFIGFS_RNDIS`, `SYSVIPC`, `FHANDLE`. With the host's clang 23 you need `HOSTCC="clang -Wno-error=incompatible-pointer-types ..."` and `KCFLAGS="-Wno-error ..."` (clang 16+ turns those warnings into errors). The stock kernel has **no** `DEVTMPFS` (pmOS requires it).

- **Finding of 2026-10-24: the ABL only runs images with header v3.** Test H3 (a kernel whose first instruction is `PSCI SYSTEM_OFF`): with **v0** the device reboots in ~2 s (the kernel never runs); with **v3** it powers off (charging screen). All the v0 tests in the matrix were invalid because of this, and the "reset in ~2 s" symptoms came from the ABL, not from the kernel.
- With v3 the DTB comes from `vendor_boot` (the stock one has 1 DTB, a 1.6 KB vendor ramdisk and the cmdline; the Lineage recovery lives in the `boot` ramdisk). For mainline: generate a v3 `vendor_boot` with our DTB using the same parameters as the stock one (`unpack_bootimg --format mkbootimg` on `vendor_boot_b.img`: pagesize 4096, base 0, kernel `0x8000`, ramdisk `0x1000000`, tags `0x100`, dtb `0x1f00000`).
- **Slot `a` is no good for tests:** even with stock `vendor_boot_a` and `dtbo_a`, H3 in v3 does not run on it (the device falls back to the slot `b` Lineage). The custom `vendor_boot` tests done on slot `a` on 24/10 (our DTB, empty or stock ramdisk, `dtbo` with an empty overlay) are **invalid**; repeat them on slot `b`.
- Android confirmed through `getprop` (24/10): **LineageOS 22.1, Android 15** (`lineage_hanoip-userdebug 15`), slot `b`.
- In the ABL, the base DTB of the stock `vendor_boot` has `board-id <0 0>` and `qcom,msm-name`; the board's `board-id` (`<0x4c 0xb200>`) comes from one of the 3 overlays in `dtbo` (the others are `0xb100` and `0xa100`). `$HANOIP_TEST_DIR/v3/dtbo-hanoip-empty.img` is a valid `dtbo` with an empty overlay for `<0x4c 0xb200>`.
- Test images: `$HANOIP_TEST_DIR/v3/` (`vendor_boot-hanoip.img`, `boot-debug-v3.img`). Diagnostic tests (loop at the entry point, loop in `start_kernel`, `SYSTEM_OFF`) in `$HANOIP_TEST_DIR/clkignore/`.

- Kernel 6.6.0-rc1-sm7150 + our DTS + test initramfs: the device resets and no USB gadget appears.
- U-Boot (sm7150-mainline/u-boot, sdm845-based branch) + our DTB: resets, no fastboot gadget.
- Control with the stock `boot_b.img`: Android boots (USB 22b8:2e82), then slows down and reboots by itself. The reset is **not specific to our images**.
- Full matrix (12 tests) in `docs/MAINLINE.md`. **All** variations through the official pmOS flow failed the same way: kernels 6.6, 6.13.4 and 7.1_rc3 (pmOS config, `EFI_ZBOOT=y`), header v0 + appended DTB and v3, original and zeroed `dtbo`, `pmbootstrap flasher boot`, U-Boot. `172.16.42.x` and the USB gadget never showed up. Image format and `dtbo` alone do not explain it.
- With header v3, the ABL uses the DTB/cmdline/ramdisk of the stock `vendor_boot` (which DTB the kernel receives is unverified); with v0 the stock `dtbo` corrupts the appended DTB unless it is zeroed. Both combinations were tested.
- Unconfirmed hypotheses: a hang before pstore/USB/framebuffer (watchdog, reserved memory, DTB handed over by the ABL); the ABL choosing the DTB by `qcom,board-id`/`msm-id` and rejecting ours.

## pstore

- Access: `adb shell su -mm -c ...` (KernelSU; plain `su` gets permission denied on `/sys/fs/pstore`).
- `dmesg-ramoops-0.enc.z` is encrypted by Motorola and unreadable. `pmsg-ramoops-0` only has Android logcat.
- No marker from our kernel ever appeared. Do not rely on pstore: use a visible console (UART) or a logger on an unencrypted partition.
- The stock Android **consumes** the records when it boots. Raw RAM does not work either: the stock kernel has no `/dev/mem`, `/dev/kmem` or `/proc/kcore`, and `/proc/iomem` is denied.
- There is no dedicated `recovery` partition (only `boot_*` and `vendor_boot_*`; the recovery lives in the ramdisk). On 2026-10-18 `fastboot reboot recovery` caused a bootloop (cause unproven) and a TWRP image for Android 11 (a valid Android boot image) **did not boot** with `fastboot boot`.
- The recovery is **LineageOS 22.1**'s (`lineage_hanoip-userdebug 15`), and `vendor_boot_b` equals the old backup: the installed Android is probably LineageOS 22.1 (Android 15) with the Cybertron kernel, not the stock Android 12 (the "Android 12" in `fastboot getvar` is stale bootloader information). Confirm with `getprop` on Android.
- That recovery uses the slot's `dtbo`: with `dtbo_b` zeroed it does not come up (this was the cause of the 18/10 bootloop). Restore `dtbo_b` before `fastboot reboot recovery`.
- Reading pstore in the recovery works: adb stays `unauthorized` until you enable **Advanced > Enable ADB** in the menu and restart the adb server on the PC; after that it is root. The recovery kernel has `CONFIG_PSTORE{,_CONSOLE,_PMSG,_RAM}=y`, ramoops at `0xaf000000`, size `0xbf800`, 256 KB console and pmsg, `ecc=0`: the console zone matches the one in our DTS.
- Test of 23/10 (kernel 7.1 zboot): `console-ramoops-0` in the recovery was still from the previous 4.14 kernel (retained RAM, with a few corrupted bits). Our kernel never initialized ramoops, consistent with the ABL being unable to load the zboot.
- **Since 2026-10-23, `adb reboot recovery` enters a LineageOS recovery** (reported by the user). Unverified: how it was installed, its adb access and whether it has `CONFIG_PSTORE_*`. It is the guide's way to read the log: after a failed mainline `fastboot boot`, reboot straight into that recovery (not into Android, which consumes pstore) and read `/sys/fs/pstore/dmesg-ramoops-0`.

## Findings of the previous session (2026-10-18)

- Tapping bootloader > Start dropped the device into the **stock recovery** (USB `18d1:d001`, adb `unauthorized`, fastboot unresponsive). *Reboot system now* in the recovery took it back to Android (slot `_b`, `boot_completed=1`, bootreason `reboot,userrequested,recovery`).
- `dtbo` does **not** contain the recovery (it is only a DT overlay; the recovery lives in the boot/vendor_boot ramdisk). `dtbo_a` and `dtbo_b` match the backups (equal hashes), so they were not the cause.
- Current `misc`: first 16 KB all zeros, no pending command. The `misc` backup starts with `bootonce-bootloader`. The hash differs only because of that. **Do not write the `misc` backup back as it is** (it would drop the device into the bootloader once); zeroing those bytes is safer.
- The cause of the drop into the recovery is **unproven**. Hypothesis: a BCB with a pending recovery command after the tests and the spontaneous reboot. The recovery reboot cleared `misc`, so it cannot be confirmed.
- If the in-use slot's `dtbo` is zeroed, that slot's Android does not boot: restore it before `fastboot continue`.

## UART

- Stock serial console (`ttyMSM0`, 115200 8N1): GPIO44 (TX) and GPIO45 (RX), function `qup12`, **1.8 V**.
- The user has **no physical access** to the board, so UART is ruled out for now.

## Battery percentage: the QG fuel gauge needs a userspace daemon (2026-10-28)

The PM6150 fuel gauge driver (`qpnp-qg`) does not compute the state of charge after boot. At boot it sets it once, from the value saved in the PMIC (SDAM) when that is recent, or from the power-on OCV looked up in the battery profile. After that it only hands voltage and current samples to userspace through `/dev/qg`, about once a minute, and waits for userspace to write the state of charge back. On Android a proprietary daemon does it. Without one, `capacity` never moves.

What that caused (2026-10-26 to 2026-10-28): `capacity` read 100 % for days while the battery drained (3.69 V under load). The charge limit waited for 60 % that never came, the phone ran on battery until it died, the PMIC lost SDAM (learned capacity and the cycle counter went back to design values and 0), and after the next boot `capacity` stayed at 1 % while charging at 3 A.

`hanoip-qgd` (device package, OpenRC, on by default) is the replacement. It is one Rust file, `hanoip-qgd.rs`, built with `rustc` alone (std only, no cargo or crates); it was Python until 2026-11-01, with the same logic:
- It reads `struct qg_kernel_data` from `/dev/qg` and counts the charge in the samples (µA × count × interval ms / 3.6e9 = mAh), over the profile's FCC (6174 mAh at 25 °C, from `BPIOCXFCC` on `/dev/qg_battery`), scaled by the learned `charge_full`.
- Below 0.5 A it pulls the count toward the profile's SOC-OCV table (`BPIOCXSOC`, OCV ≈ V + I × ESR), 2 % of the gap per batch; a PMIC rest measurement (`QG_GOOD_OCV_UV`) pulls 50 %. A `Full` charger status sets 100 %.
- It writes `QG_SYS_SOC`, `QG_CC_SOC` and `QG_BATT_SOC` (0-10000) back. The kernel ramps `capacity` toward it 1 % at a time and saves it to SDAM, so the next boot starts from it.
- Where it starts: the value in `/run/hanoip-qgd.soc` after a restart, the kernel's boot value if it starts within 5 minutes of boot, otherwise an OCV estimate (rough while charging: it read 51 % when the charge since boot gave 29 %).
- `scripts/test-qgd` runs the tests in `hanoip-qgd.rs` (`rustc --test`): the arithmetic and the struct layout (412 and 144 bytes), without the phone.
- On the phone since 2026-11-01 (release `v0.1.3`; built with `scripts/pmb build --force device-motorola-hanoip` after `scripts/setup-pmaports`, copied over and installed with `apk add --allow-untrusted --no-network`): about 1 MB RSS against 7.7 MB for the Python one, and it resumed from `/run/hanoip-qgd.soc` and kept writing batches. The Python version is kept on the phone as `/var/lib/hanoip/hanoip-qgd.py`; to go back, copy it over `/usr/bin/hanoip-qgd` and `rc-service hanoip-qgd restart`.

- **Kernel modules did not load at all; fixed (patch `0010`, issue #24).** `load_module()` ORed `MODULE_INIT_IGNORE_MODVERSIONS` and `MODULE_INIT_IGNORE_VERMAGIC` into the caller's flags (a `//FIXME` of the vendor tree, there for prebuilt modules from another build) before anything else. With `MODULE_SIG_FORCE=y` and `MODULE_FORCE_LOAD` off that refused every module in two steps: `module_sig_check()` verifies a signature only when `flags == 0`, so it never verified and its initial `-ENOKEY` stood (`Required key not available`, silent, for a signature that was valid and made by the kernel's own key), and, once that was out of the way, `check_modinfo()` turns the vermagic check into `try_to_force_load()` when `IGNORE_VERMAGIC` is set, which returns `-ENOEXEC` without `MODULE_FORCE_LOAD` (`Exec format error`). Patch 0010 removes the two forced flags; every module of this kernel is built with it, so the stock checks pass. Checked on the phone: `finit_module` of `lcd.ko` returned 0, `modprobe rdbg` loaded, `rmmod` unloaded both, `tainted` unchanged. Finding it took a throwaway build that returned a different errno at each failure point, because this kernel's log buffer does not keep what the kernel prints after boot: writing to `/dev/kmsg` returns success and the line never shows in `dmesg`, whatever the console loglevel. So an empty `dmesg` after a failure proves nothing here. The module tree must come from the same build as the running kernel (`scripts/push-modules` checks the release, not the build).
- **Watchdog**: `WATCHDOG` and `SOFT_WATCHDOG` give `/dev/watchdog`. `busybox watchdog -T 10 -t 60 /dev/watchdog` (timeout 10 s, never fed in time) restarted the phone: it stopped answering after about 15 s and was back about 45 s after the start, uptime reset, services up, slot b successful, the PMIC logged a hard reset. A flash of `boot_b` also needs `scripts/push-modules` only for the module tree; with `br_netfilter` built in, nothing that matters for containers is a module.

**Zram swap (2026-11-01, issue #8).** `postmarketos-zram-swap` never started on this kernel, for three reasons, all found by running its `zramstart` by hand: (1) it asks for zstd and zram offers only what the crypto API has, while `CONFIG_CRYPTO_ZSTD` was off even though the tree has `crypto/zstd.c` and `zcomp.c` lists it: now on (`ZSTD_COMPRESS`, `ZSTD_DECOMPRESS` and `XXHASH` come with it); (2) it runs `modprobe zram` under `set -e`, and the kernel package installed no `/lib/modules`, so `modprobe` failed with zram built in: the package now installs the module tree (10 modules, `modules.builtin`, `modules.dep`, run through `depmod`; kbuild's `modules_install` could not be used because pmbootstrap `--envkernel` hands the source tree to the build user read-only); (3) it sets `vm.swappiness=180` and the kernel rejected anything over 100: patch `0008` raises the limit to 200 without turning on `CONFIG_OPLUS_MM_HACKS`, which also changes direct reclaim (`file_prio` is `200 - swappiness`, so both priorities stay non-negative). `scripts/test-kernel-config` fails while any of the three is missing. The default of `zramstart` is already zstd, so `deviceinfo` is untouched; to change it set `deviceinfo_zram_swap_algo` (and `deviceinfo_zram_swap_pct` for the size, 150 % of RAM by default, 5.3 GB here).

Result on the phone: `/dev/zram0` zstd, 5.3 GB, priority 300 (above the 1 GB swapfile), `swappiness=180`, `page-cluster=0`, `min_free_kbytes=100000`, service `started`, and the same after an unattended reboot. `scripts/push-modules` copies the module tree to a phone that runs the matching kernel (a flash of `boot_b` does not carry it; a fresh image gets it from the kernel package). Measured with one 200 MiB sample of real files (binaries, libraries, text) written and read through `dd` on temporary zram devices, one stream, so it says nothing about contention: lzo 1.66x, 185 MiB/s write, 571 MiB/s read; lz4 1.65x, 175-189 and 625-690; zstd 2.24x, 34 and 222. zstd packs about 35 % more into the same RAM and costs about 5x the compression time and 3x the decompression time of lz4. The kernel's zstd runs at a fixed level 3, and lz4's acceleration is not exposed in 4.14, so a faster lz4 would need a kernel change; not done, because zstd was available. Not checked: the swap under real memory pressure (nothing was pushed into it), and what zstd costs the CPU there.

**Tailscale goes through a relay when the PC is on another network (found 2026-11-01).** On the same LAN `tailscale ping` is direct (`via 192.168.10.244:41641 in 2ms`) and the SSH-only-over-USB-and-tailnet rule is not involved: it blocks TCP 22 on other interfaces, and UDP 41641 (what Tailscale needs for the direct path) is accepted on every interface. When the PC sat on the Wi-Fi of another network it fell back to the DERP relay (`DERP(sao)`, 40-150 ms) and long transfers dropped (`flash-boot-ssh` needed three tries; it wrote nothing on the failed ones). The cause on the PC side is Cloudflare WARP: `ip route get <phone public IP>` goes out `dev CloudflareWARP` (table 65743), because WARP's policy rule (priority 5209) comes before Tailscale's own (5210, fwmark `0x80000` to the main table), and `tailscale netcheck` on the PC said `UDP: false`. The phone's side is fine (`UDP: true`, public IPv4, `MappingVariesByDestIP: false`). Decision: WARP is on only for the university Wi-Fi, so it is paused by hand when working with the phone off the LAN (`warp-cli disconnect`, then `warp-cli connect`); no routing rule was added, because a rule that lets Tailscale bypass WARP could stop Tailscale from reaching the relay on a network that filters it. Over a relay keep transfers short: `hanoip-ssh` gives up after about 30 s of silence (`ServerAliveInterval=10`, three tries), and nothing resumes a copy. Put the phone's Tailscale address in `HANOIP_HOST` in `.env` while the USB cable is out.

**The Telegram bot in Rust, and no python3 on the phone (2026-11-01, issue #22).** `hanoip-bot.rs` is one std-only file, built with `rustc` like the gauge daemon. Rust's standard library has no TLS, so every request goes through `curl`: the URL (which holds the token) and the form fields are written to curl's standard input as a config file (`curl -K -`), so the token is never in an argument list or in `ps` (checked on the phone while it ran: the process was `curl -K -`). On the phone `python3` is still installed (other packages may use it); only the package stopped needing it. Checked on the phone: `hanoip-bot --alert` returned 0 and the service ran a minute with no `getUpdates failed`. Not checked by me: that the commands answer on Telegram itself, which needs the owner's account (`/up`, `/status`, `/status -h`).

**Battery cycle count (2026-11-01).** A fully drained battery clears the PMIC SDAM and the 8 cycle buckets with it. Patch `0007` makes `/sys/class/power_supply/bms/cycle_counts` writable (root): it takes exactly 8 counts of 0-65535 in the format it is read in, writes them to SDAM and to the driver's RAM copy together (so the next stored cycle adds one to the restored value, with no need to reboot before a charge ends), and refuses anything else without changing anything. The generic power supply sysfs only parsed one integer, so `power_supply_sysfs.c` hands the text of this one property to the driver. `scripts/test-cycle-counts` builds the function out of the patch against stand-ins for the kernel helpers (valid, malformed, out-of-range and store-error inputs, under the address sanitizer). `scripts/restore-cycle-counts` adds the saved buckets (`HANOIP_CYCLE_BUCKETS` in `.env`) to what the phone had counted since the loss (`1 1 1 2 3 3 1 1`), writes the sum once, reads it back and leaves `/var/lib/hanoip/cycle-restored` so a second run cannot add them twice; the result was `26 61 115 150 181 170 138 86`, average 115, which is what `cycle_count` and `hanoip-status` show. The temporary offset (`/var/lib/hanoip/cycle-offset`, 114) and its code in `hanoip-status` are gone. The kernel went to `boot_b` as `linux-motorola-hanoip` pkgrel 9 (flashed from the PC with a backup of the old `boot_b`; the phone was back 50 s after the reboot, slot b successful). After a second reboot (package r27, which carries the status without the offset) the 8 values were still there, so SDAM keeps them. Not covered: a charge session ending after the restore (the next stored cycle should add one to the restored bucket; it needs a real charge from the bucket's range to see).

Found on 2026-10-29, before turning the charge limit back on:
- With the cable suspended (`input_suspend=1`) the charger keeps reporting `Full` while the battery discharges, and at `Full` on the cable the kernel sends batches with no samples. `Full` therefore sets 100 % only when the batch shows no discharge (under 100 mA) or has no samples; otherwise the percentage froze at 100 % again. A 5-minute suspended test then fell 0.62 %, and a 3-minute one 0.25 %.
- The profile table is the cell's own scale (98.5 % at the 4.42 V rest voltage of a full battery). The kernel's boot code maps the cutoff (3.4 V, the driver default, as `qcom,vbatt-cutoff-mv` is not in the DT) to 0 % and the float voltage (`bms/voltage_max`, 4.45 V) to 100 %, capped at 99 % raw. The OCV pull uses the same normalization.
- `hanoip-qgd` writes about every 62 s, but one gap of 288 s showed up right after the cable came back.
- The charge limit no longer trusts the percentage alone: if `/run/hanoip-qgd.soc` is older than 15 minutes (except while holding on the cable, where the kernel sends no samples), or the battery is under 3.75 V (about 20 %), it resumes charging and makes no cut. Its old state `0 1 0` (a cut from before the battery died) was reset to `0 0 0`.
