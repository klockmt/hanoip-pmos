# Pitfalls: what broke on this phone, why, and where it is kept from breaking again

One home for these. Each row is a problem that really happened. **Where enforced** names the test or the file that
fails or protects when the rule is broken; "docs only" means nothing checks it and the rule is the only guard.
Every bug gets an automated test that fails before the fix and passes after (`scripts/test-*`, all run by
`scripts/check-repo`). The log of how each was found is in [`NOTES.md`](../NOTES.md).

## Battery and power

| Symptom | Cause | Rule | Where enforced |
|---|---|---|---|
| Battery stuck at 100 % for days, charge limit never cut, battery died, PMIC lost its SDAM | `qpnp-qg` does not compute the charge after boot; a userspace daemon must write it back | `hanoip-qgd` must keep running. The charge limit must not trust the percentage alone: a stale gauge file (older than 15 min, except while holding on the cable) or under 3.75 V resumes charging | `scripts/test-qgd`, `scripts/test-charge-limit` |
| Percentage frozen at 100 % with the cable suspended | The charger keeps saying `Full` while the battery discharges | `Full` sets 100 % only when the batch shows no discharge (under 100 mA) or no samples, and the voltage is at least 4.30 V | `scripts/test-qgd` |
| Gauge scale off | The profile table is the cell's own scale; the kernel maps 3.4 V to 0 % and 4.45 V to 100 % | Pull toward the OCV on the kernel's scale | `scripts/test-qgd` |
| Cycle counter lost (8 buckets) | A fully drained battery clears the PMIC SDAM | Never let the battery die. If it happens, `scripts/restore-cycle-counts` (needs kernel patch 0007, which makes `bms/cycle_counts` writable) | `scripts/test-cycle-counts`, `scripts/test-restore-cycle-counts`, `scripts/test-status` |
| "Not charging" with `usb/online=0` read as no power | In the limiter's hold the input still feeds the phone | Look at `usb/input_current_now`, not `usb/online` | `scripts/test-status` (the bypass line) |
| Writing `none` to the front LED's `trigger` fails with `Invalid argument`, so a script cannot hand the LED back to manual control | This LED driver (`/sys/class/leds/charging`) rejects `none`, and the kernel timer turns the LED off if either delay is 0 | Use another trigger that never fires (`kbd-scrolllock`) and write `brightness` for solid; the `timer` trigger is only for the flash | `scripts/test-led` |
| The front LED stays dark while a cable is in, but flashes on the battery, although `brightness` reads 255 | The `timer` trigger with `delay_on` 600000 and `delay_off` 1 (the first "solid") does not light this LED while USB power is present, and the sysfs values still read as set. Found by eye on 2026-11-04: a direct `brightness` write under a trigger that never fires lights it | Solid is `kbd-scrolllock` plus `brightness` 255, never a long timer; check an LED change by looking at the LED, not at sysfs | `scripts/test-led` (the fake sysfs only proves what is written) |

## Network, firewall and Tailscale

| Symptom | Cause | Rule | Where enforced |
|---|---|---|---|
| SSH dropped, load 3-4, conntrack full (65,536) | Tailscale rewrote `resolv.conf` to its own MagicDNS and looped | `tailscale up --accept-dns=false`; a boot script turns it off if it was left on; `hanoip-status` warns | `scripts/test-tailscale-dns`, `scripts/test-status` |
| nftables rules with `{ ... }` fail with "Not supported" | The set backends were missing | Keep `NFT_SET_HASH/RBTREE/BITMAP` as `=y` | `scripts/test-kernel-config` |
| SSH answered on Ethernet and Wi-Fi too | pmOS's `50_sshd.nft` accepts port 22 from every interface | `02_hanoip-ssh.nft` loads first and accepts only `usb*` and `tailscale0` | `scripts/test-firewall` |
| Tailscale's firewall file was hand-made and opened UDP 41641 on every interface | Nothing packaged it | `52_hanoip-tailscale.nft` accepts that port only on `eth*` and `wlan*`; the package depends on `tailscale` and removes the old file on install | `scripts/test-firewall` |
| Tailscale on a relay, long copies dropping | Cloudflare WARP on the PC takes Tailscale's UDP when the PC is on another network | Pause WARP off the LAN; keep transfers short over a relay | docs only (see HOMELAB) |
| Large transfers over the USB (NCM) network take it down until a reboot | Cause not found (issue #2) | Throttle to 1 MB/s (`pv -L 1m`); a script that feeds a file into `hanoip-ssh` without it needs a `# small` comment | `scripts/test-throttle` (every script), `scripts/test-flash-boot-ssh` |
| During a mainline RAM test the PC lost `172.16.42.2` a minute after it was set by hand, and the shell went silent | The test initramfs runs no DHCP server; NetworkManager's DHCP on that interface failed and flushed the address (2026-11-07) | Before setting the address, `nmcli device set <if> managed no`; give it back with `managed yes` once the server is up again | docs only |
| The mainline kernel booted through U-Boot got none of the U-Boot DTB's `bootargs` (`panic=5`, `console=ttyGS0`) | U-Boot hands over only the boot image's command line (2026-11-07) | Put every needed argument in the boot image's command line | docs only |

## Boot, slots and flashing

| Symptom | Cause | Rule | Where enforced |
|---|---|---|---|
| Userspace hang or a network that never came back needed someone at the phone | Nothing fed `/dev/watchdog` | `hanoip-watchdog` feeds it and stops on purpose when the gateway is silent for 5 minutes; at most 3 resets in a row and none in the first 15 minutes, so a dead router is not a boot loop. Never `kill -9` it: the watchdog stays armed | `scripts/test-watchdog` |
| Phone gone after about 7 reboots | pmOS never marks the A/B slot successful; the ABL makes slot b unbootable and flips to a | `qbootctl -m` at every boot (from `/etc/local.d`). Recovery: `fastboot getvar slot-unbootable:b` (check first), `fastboot set_active b`, `fastboot reboot`, and say what was done | docs only (needs the phone) |
| ABL never ran the mainline kernel | The ABL only runs header v3 and only `Image`/`Image.gz`, not EFI zboot | `EFI_ZBOOT` off, a v3 `vendor_boot`; the earlier v0 tests are invalid | docs only (mainline is long term, issue #6) |
| `fastboot flash userdata` refused | Motorola's fastboot | Write the rootfs through the Lineage recovery with `dd` and verify the hash | docs only |
| Kernel upgrade would flash an old cmdline | The subpackage `-kernel-downstream` owns `deviceinfo` and was left at r0 | Install the main device apk and its subpackage together | docs only |
| Phone hung at boot after `boot-deploy` regenerated `vendor_boot` | `console=tty0` first in the command line, where the vendor_boot that boots has `console=ttyMSM0,115200n8` (issue #21, tried on the phone 2026-11-02) | The command line starts with `console=ttyMSM0,115200n8`; updates flash `boot`/`vendor_boot` again; back up to the PC before any flash by hand, and check `boot_b` and `vendor_boot_b` after an `apk add` | `scripts/test-deviceinfo`; hashes checked by hand |
| `flash-boot-ssh` stopped at its first root command and pushed 64 MB with no limit | Plain `sudo` over the BatchMode login cannot ask for a password; no `pv` | Root commands through `hanoip-sudo`, transfers through `pv -L 1m` | `scripts/test-flash-boot-ssh` |
| The mainline root in super's region failed to mount: I/O errors writing `loop7` (2026-11-07) | The stage-1 loop that locks every disk ran while the UFS LUNs probed, before `super` had a name, and locked `super` and its disk; the lock never unlocks. Nothing was written | Start the locking loop only once `super` is known, make `super` and its disk writable explicitly before the bounded loop, and lock everything else | `scripts/test-mainline-ram-image` |
| On mainline the modem service stopped with "cannot read fsg" (2026-11-07) | The `fsg` link is made on 4.14 by the `-modem` subpackage's udev rule; mainline only has `fsg_a` and `fsg_b` (identical copies on this phone) | `hanoip-ml-modem` falls back to `fsg_b`, then `fsg_a` | `scripts/test-mainline-root` |
| On mainline the ADSP came up but the modem stayed `offline`, so no Wi-Fi (2026-11-07) | The PAS driver starts the ADSP by itself but not the modem (`rmtfs -s` would) | `hanoip-ml-modem` starts it through sysfs once its recovery is off | `scripts/test-mainline-root` |
| On mainline the clock read 1974 and Tailscale stayed "logged out" (2026-11-07) | The PMIC RTC does not keep the time, and chronyd started before the Wi-Fi could not resolve its pool, so it had no source and TLS failed | `swclock` instead of `hwclock`; a NetworkManager dispatcher script restarts chronyd when a connection comes up | `scripts/test-mainline-root` |
| The persistent U-Boot sat at its `=>` prompt for good and the user had to hold the power key (RAM test, 2026-11-08) | A key is already pending when autoboot starts (`stop autoboot:  0 ^H^H^H 0` in U-Boot's own console), and with `bootdelay=0` that stops the boot. The first, RAM-only environment got past it with `bootretry=1`; the persistent one had `-1` | `bootdelay=-2`: autoboot without looking for a key | `scripts/test-mainline-uboot` |
| U-Boot would have booted whatever sits at boot_a's offset on LUN 0 | `scsi read` reads the current device and `part number` does not change it: boot_a is on LUN 4, the current device stays 0 | `scsi dev $ml_dev` before `scsi read` | `scripts/test-mainline-uboot` |
| Nothing reset the phone from that prompt, and a kernel hung before stage 1 would not have been reset either | U-Boot fed the watchdog (`CONFIG_WATCHDOG=y`) and its handoff stopped it (`wdt_stop_all()`) | Nothing in U-Boot feeds the watchdog and it keeps running into the kernel, whose `qcom_wdt` pings it until stage 1 opens it; the Volume Down menu stops it before it waits for a person | `scripts/test-mainline-uboot` |
| Three U-Boot debug sessions showed no fastboot and no serial gadget, which looked like a UFS hang (2026-11-08) | The same pending key stopped them at the prompt. One of them also waited for `product: motorola-hanoip` (U-Boot answers `hanoip`) with a `fastboot getvar`, which waits forever when no device shows | Read U-Boot's own console first (`fastboot oem console`); poll `lsusb` with a timeout, never a bare `fastboot getvar` | docs only |
| A mainline root that stalled before `local.d` sat 10 minutes with no `usb0` and no Wi-Fi until the user held the power key (2026-11-08; not seen again in three boots, cause unknown) | The stage-1 daemon feeds the watchdog whatever the root does, and the dead men run only from `local.d` or from a failed stage 1 | Stage 1 reboots a root that has not written `/run/hanoip-ml-up` (local.d's last step) 5 minutes after `switch_root`, and leaves the OpenRC services and the kernel log in `/var/log/hanoip-ml-deadline.log` | `scripts/test-mainline-root` (runs the function in a namespace) |
| `scripts/mainline-make-root` stopped at the mount: "wrong fs type, bad superblock" (2026-11-08) | After an unclean mainline shutdown the ext4's orphan file holds inodes (`orphan_present`), and the 4.14 kernel cannot mount that read-write ("unsupported optional features (10000)") | `e2fsck -p` on the bounded loop before the mount | `scripts/test-mainline-root` |
| The mainline kernel log held only "disallowed SPMI write to sid=0, addr=0x6046", about 30 a second, and none of the boot (2026-11-08) | chrony's `rtcsync` makes the kernel set the PMIC RTC, which the PMIC arbiter does not let Linux write, and the kernel kept retrying | No `rtcsync` in the mainline root's `chrony.conf` | `scripts/test-mainline-root` |
| `qbootctl` with no arguments, run on mainline as a read-only look, tried to write the GPT; the guard stopped it (2026-11-08) | Moving from one disk's partitions to the next, it writes back the GPT it had open; and `-m` marks every partition of the slot, on each disk that holds one (LUN 4 and LUN 2 for slot a) | On mainline only `98-hanoip-ml-slot.start` runs it, with only those whole disks lent; read the slots with `fastboot getvar` or a dump of the GPT sectors | `scripts/test-mainline-root` |
| A boot's log missing from `logbookd.db` | logbookd writes only on a clean shutdown; the raw `reboot()` syscall skips it | Use `reboot` when the log matters | docs only |
| `dmesg` empty after a failure | This kernel's log buffer drops what the kernel prints after boot (a write to `/dev/kmsg` returns success and never shows) | An empty `dmesg` proves nothing here; a throwaway build that returns a different errno at each point worked | docs only |

## Kernel

| Symptom | Cause | Rule | Where enforced |
|---|---|---|---|
| Every boot took about 3 minutes | Each missing firmware file waited 60 s | Keep `FW_LOADER_USER_HELPER_FALLBACK` off | `scripts/test-kernel-config` |
| `dtc` segfaults | The tree's own `dtc` built with clang 23 | Build with `DTC=/usr/bin/dtc` | `scripts/build-kernel` |
| `losetup -P --sector-size 4096` makes no `loopNpX` | The loop device does not rescan after `LOOP_SET_BLOCK_SIZE` | Keep kernel patch 0001 | `scripts/check-repo` (the patch copies are identical); no behavioural test |
| Wi-Fi firmware crashed about 0.7 s after WLFW connected (`EX:kernel:0x0:tmr_slave1`) | The modem reads SMEM item 134, created by `mmi_info`, which was off | Keep `CONFIG_MMI_INFO=y` and `CONFIG_MMI_ANNOTATE=y` | `scripts/test-kernel-config` |
| `postmarketos-zram-swap` never started | No `CRYPTO_ZSTD`, no `/lib/modules` for `modprobe zram`, and `vm.swappiness=180` rejected over 100 | Keep `CRYPTO_ZSTD=y`, the module tree in the kernel package and patch 0008; `scripts/push-modules` for a phone that already runs the kernel | `scripts/test-kernel-config` |
| `BTRFS_FS=y` stopped the build in `fs/btrfs/inode.c` | This tree has `timespec64` inode times and `fs/btrfs` did not | Keep patch 0009 | `scripts/test-kernel-config` |
| `modprobe` fails with "Required key not available", then "Exec format error" | The vendor `load_module()` forced `IGNORE_MODVERSIONS` and `IGNORE_VERMAGIC`: the signature was never checked (`-ENOKEY` with `MODULE_SIG_FORCE`) and `check_modinfo()` refused the vermagic (`-ENOEXEC`) | Keep patch 0010; load only modules from the same build as the kernel | `scripts/test-kernel-config` |
| `runc` panics (`/proc/thread-self` candidate) | The libpathrs in current runc needs newer kernel APIs than 4.14 | Use `crun` | docs only |
| Load near 9 with the CPUs idle, SSH logins slow or timing out, `reboot` hanging; `dmesg`: `elogind-daemon` in `__list_add_valid` from `psi_trigger_create`, then `rcu_sched` stalls on one CPU (three boots in a row, 2026-11-07, #31) | elogind's sd-event writes a memory-pressure trigger to its cgroup's `memory.pressure`, and this kernel's PSI backport corrupts a list there; the CPU then spins on the trigger mutex forever. Userspace still feeds `/dev/watchdog`, so no watchdog resets the phone | elogind runs with `MEMORY_PRESSURE_WATCH=/dev/null`. It is started by D-Bus activation, which clears the environment, so the package overrides its D-Bus service file in `/usr/local/share/dbus-1/system-services` (read first); `/etc/conf.d/elogind` does not work. Out of the hang: the sysrq reboot (`echo b > /proc/sysrq-trigger`) | `scripts/test-elogind` |

## Storage (the NAS disk)

| Symptom | Cause | Rule | Where enforced |
|---|---|---|---|
| A btrfs disk formatted on the PC mounts read-only on the phone | `mkfs.btrfs` v7 turns on `block-group-tree` (`compat_ro` bit `0x8`); the 4.14 btrfs does not know it and mounts unknown `compat_ro` features read-only | Format with `mkfs.btrfs -O ^block-group-tree`, or `btrfstune --convert-from-block-group-tree` on the unmounted fs. Before plugging it in, `btrfs inspect-internal dump-super <dev>`: `compat_ro_flags` must not have `0x8` | docs only |
| Reading one area of the USB HD fails with `Input/output error` and the disk drops off the bus (`Synchronize Cache failed`) | A damaged stripe of the platter: SMART `Current_Pending_Sector` rose from 1 to 148 with `UDMA_CRC_Error_Count` flat, so it is not the cable. Every read of the zone stalls the drive and the USB bridge resets | Leave the zone out of every partition (layout in [`HOMELAB.md`](HOMELAB.md)); never repartition it back or scan the gap again; keep only data that is reproducible or has another copy; `btrfs scrub` now and then | docs only |
| The HD is gone from `lsblk` and `smartctl` says `No such device`, while the kernel log fills with btrfs errors of a `<missing disk>` | The drive or its USB bridge dropped; the old mount stays in the kernel | Power-cycle the drive; `umount -l` the stale mount; read 20 MB with `dd` before starting anything long; check model and serial with `smartctl -i` before writing a partition table | docs only |
| Minutes after mounting, a write fails with `Read-only file system`; `dmesg` shows `bdev ... errs: wr N` and `forced readonly`, and the disk came back as another name (`sdg` became `sdh`) | The whole USB hub re-enumerated (`usb 1-1: new high-speed USB device`, the hub also takes the Ethernet adapter down). The hub has done this many times since the first disk tests, with no disk access going on. btrfs saw write errors and went read-only; nothing on disk was damaged (scrub clean, SMART unchanged) | Mount by `LABEL=`, never by `/dev/sdX`; after a drop, stop the services that use the disk, `umount`, `mount -a`, scrub. The cause of the hub resets is still open | docs only |
| Samba or Syncthing writes into an empty mount point and fills the phone's own flash while the HD is away | `nofail` lets the boot go on without the disk, and the services then see a plain directory on the root filesystem | `chattr +i /mnt/hd-a /mnt/hd-b` while they are unmounted (a write then fails with `Operation not permitted`); Syncthing also refuses a folder without its `.stfolder` marker | docs only |
| A SMART self-test ends as `Aborted by host` | The drive was powered off or dropped during the test | Start it again and leave the disk alone until it ends (about 77 minutes for the extended test) | docs only |

## Packaging

| Symptom | Cause | Rule | Where enforced |
|---|---|---|---|
| `hanoip-qgd` and `hanoip-bot` missing on a fresh image | `python3` was not in the package's `depends`; the phone only had it by chance | Declare the interpreter of every shipped script, and drop it once none is shipped. Both daemons are Rust now: the package needs `curl`, not `python3` | `scripts/test-apkbuild-depends` |
| `abuild` called `deviceinfo` corrupted | `sha512sums` was not in the order of `source=`; abuild pairs them by position | Keep the same order | `scripts/test-apkbuild-sums` |
| Package build died before abuild, installing `firmware-qcom-sm7150` in the x86_64 chroot | `rust` in `makedepends` makes pmbootstrap use crossdirect, which installs every dependency natively | `options=!pmb:crossdirect` on a package that builds Rust | `scripts/test-apkbuild-depends` |
| On a fresh install `hanoip-bot` panics and restarts every 5 s, forever | There is no `/etc/hanoip/telegram.env` yet, the bot panics reading it, and `supervise-daemon` has no restart limit | `start_pre` in the init script refuses to start while the file is missing | `scripts/test-bot` (section 4) |
| Modem/Wi-Fi userspace missing on a fresh image, `fsg` linked to `fsg_b` only | The files were installed by hand and the udev rule hard-coded the slot | The `-modem` subpackage; the rule reads `androidboot.slot_suffix` | `scripts/test-modem-package` |
| A private value in a tracked file | Nothing looked for it | A 15-digit number (IMEI-like) and the login user are flagged, along with MACs, serials and home paths | `scripts/check-repo`, `scripts/test-check-repo` |
| The mainline subpackage built on this PC and failed on a clean clone (2026-11-08) | The commit changed only the `APKBUILD`: its thirteen files, copies of `kernel/mainline/root-overlay`, stayed in the working tree. `check-repo` looked for each source on disk, never in git | Commit a source with its `APKBUILD`; a copy of a file that lives elsewhere gets a test that compares the two, and `check-repo` refuses a source git does not track | `scripts/check-repo`, `scripts/test-check-repo`, `scripts/test-device-mainline-subpackage` |
| The mainline root's clock stayed wrong after the Wi-Fi came up | NetworkManager's dispatcher for chrony was installed 0644, and NM only runs a dispatcher it may execute. The overlay's copy is 0755, which hid it | Install what a service executes as 0755 and configuration as 0644, and check the mode, not only the path | `scripts/test-device-mainline-subpackage` |
| A script that changes state ran without a dry run | Four scripts had no `DRY_RUN` | Every state-changing script takes `DRY_RUN=1` | `scripts/test-dry-run` |
| Debugging a script with `sh -x` printed every value of `.env`, passwords included, into the terminal (2026-11-07) | `env.sh` loads `.env` with an `eval`, and the trace of that `eval` shows each `export NAME="value"` | `env.sh` turns tracing off around the `eval` and back on after it. A trace of your own lines can still show values you expand, so never share one | `scripts/test-env-xtrace` |

## The pmOS flow (found on 2026-10-18)

| Symptom | Cause | Rule | Where enforced |
|---|---|---|---|
| Conflicting `deviceinfo` and `machine-info` files | The device package depended on the generic `device-qcom-sm7150` | Do not depend on it. What works: `android-tools`, `firmware-qcom-sm7150`, `mkbootimg-osm0sis`, `postmarketos-base`, `soc-qcom` (the old `soc-qcom-sm7150` no longer exists) | docs only |
| `boot-deploy` fails | It needs `android-tools` in the rootfs when `deviceinfo_generate_bootimg="true"` | Keep `android-tools` in `depends` | docs only |
| pmOS generated a header v0 `boot.img` | `deviceinfo_header_version` was not set | Set it (3 for this phone) | docs only |
| The generated `boot.img` does not boot | `CONFIG_EFI_ZBOOT` on packs `vmlinuz.efi`, which the ABL cannot load | Check `$PMB_WORK/chroot_rootfs_motorola-hanoip/boot/boot.img`: the kernel starts with `1f8b` (gzip) | docs only |
| The build is wiped when packaging | Packaging **with** envkernel active runs `mrproper` | Package without activating envkernel (`pmbootstrap build --envkernel <pkg>`, nothing else) | docs only |
| A change to `deviceinfo` or the APKBUILD is ignored | The checksums and the built package were stale | `scripts/update-apkbuild-sums` (or `pmbootstrap checksum`), then `build --force`, then `install`. On `umount ... exit 32`, repeat `shutdown` or use `zap` | `scripts/test-apkbuild-sums` |
| `git clone` from GitHub fails here (`SSL_read unexpected eof`) | Unknown | Use `curl` with tarballs from `codeload.github.com` | docs only |
| The recovery shows up, or `misc` sends the phone to the bootloader once | The `misc` backup starts with `bootonce-bootloader` | Do not write the `misc` backup back as it is; zero those bytes first. Zeroing the in-use slot's `dtbo` stops that slot's Android: restore it before `fastboot continue` or any reboot | docs only |
